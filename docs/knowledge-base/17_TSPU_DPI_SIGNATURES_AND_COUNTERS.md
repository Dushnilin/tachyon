# 17. Промежуточные сетевые фильтры (Middlebox / DPI) и профили десинхронизации

## 1. Архитектура и принципы работы сетевых фильтров на маршруте

Промежуточные сетевые узлы (middlebox / системы глубокой инспекции пакетов DPI) анализируют заголовки и начальные пакеты соединений на сетях операторов связи.

### Основные режимы фильтрации на маршруте:
1. **Пассивный анализ (In-line / TAP):** транзитный узел анализирует зеркалированный трафик. При совпадении сигнатуры SNI или HTTP-заголовка генерирует и инжектирует пакет `TCP RST` в обе стороны соединения.
2. **Активный сброс (In-line Drop):** фильтр установлен в разрыв канала и отбрасывает пакеты сессии, вызывая `Connection Timeout` или `EOF`.
3. **Ограничение полосы (Шейпинг по L7-сигнатурам):** искусственное ограничение пропускной способности (например, до 128 Кбит/с) при обнаружении определённых потоков данных (например, `googlevideo.com` CDN).

## 2. Анализ профилей фильтрации по ключевым сервисам

### 2.1. YouTube (GoogleVideo 4K деградация потока)
- **Механика фильтрации:** транзитный узел анализирует TLS ClientHello при обращении к CDN-нодам `rr*.googlevideo.com`. При совпадении сигнатуры фильтр переводит TCP-сессию в режим ограничения скорости или отбрасывает видеочанки.
- **Профиль оптимизации:**
  - `multisplit:pos=1,midsld:seqovl=1:fooling=badseq` (Zapret v2)
  - `fake,split2:pos=1:ttl=8:fooling=badseq` (Zapret v1)
  - Сплит на `midsld` разделяет домен `googlevideo` на два TCP-сегмента, предотвращая срабатывание строкового сигнатурного анализатора.

### 2.2. Discord (Gateway + Голосовые каналы RTC)
- **Механика фильтрации:** затрагивает два уровня трафика:
  1. TCP 443 — шлюз сообщений и API (`discord.com`, `gateway.discord.gg`).
  2. UDP 50000-65535 — голосовые сессии WebRTC / Voice.
- **Профиль оптимизации:**
  - Мультипрофиль `zapret2`:
    - Для TCP 443: `--filter-tcp=443 --filter-l7=tls --payload=tls_client_hello --lua-desync=multisplit:pos=1,sniext+4:seqovl=1:fooling=badseq`
    - Для UDP Voice: `--filter-udp=3478-3480,50000-65535 --filter-l7=discord,stun --payload=discord_ip_discovery,stun --lua-desync=fake:blob=discord_udp:repeats=6`
    - Для игрового / произвольного UDP (Fortnite, кастомные сессии): `--filter-udp=1024-65535 --out-range=-d2 --lua-desync=fake:blob=stun_fake:payload=all` (параметр `:payload=all` обязателен, иначе неизвестный L7-трафик пропускается без фейков)

### 2.3. Instagram & Meta (TLS 1.3 / ECH)
- **Механика фильтрации:** сброс TCP-соединения инжекцией RST-пакета сразу после получения первого ClientHello с открытым SNI `instagram.com`.
- **Профиль оптимизации:**
  - Низко-TTL фейк с `fooling=badseq` или `fooling=md5sig`, за которым следует сегментированное TLS-рукопожатие. Транзитный фильтр обрабатывает фейковый пакет и сбрасывает контекст инспекции, пропуская последующий реальный запрос.

### 2.4. Веб-ресурсы со сбросом сессии по HTTP/HTTPS SNI
- **Механика фильтрации:** HTTP-перенаправление (302 Redirect) или `TCP RST` при анализе поля HTTPS SNI.
- **Профиль оптимизации:**
  - `disorder2:pos=1` или `split2:pos=1:seqovl=1` изменяет порядок сборки заголовка HTTP/TLS на промежуточном узле.

## 3. Подбор оптимального TTL для фейковых пакетов

Для стратегий с инжекцией фейковых пакетов (`fake`) важно подобрать параметр `ttl`:
- **Слишком маленький TTL (< 3):** фейковый пакет истекает на первых узлах маршрута до достижения сетевого фильтра оператора.
- **Слишком большой TTL (> 15):** фейковый пакет доходит до целевого сервера, и сервер сбрасывает соединение из-за невалидного рукопожатия.
- **Оптимальный диапазон:** `TTL = 6..8` для большинства проводных и мобильных сетей.
